# v0.7.0 マイグレーションガイド

v0.6.0 → v0.7.0 へアップグレードする際の breaking change と対処手順をまとめます。

## 0. 概要

Phase N（N01-N09）で `internal/service/find/` 層を Phase H 仕様から完全ゼロベース再設計しました。
api 層が Phase L で BOARD API Ransack 完全準拠した結果、find 層は「api 層単独では困難な処理」（5 件特化）に絞り込んだ薄い層へ刷新されています。

主な breaking changes:

1. MCP tool 数: **12 → 11**（`find_groups` 削除）
2. enrichment セマンティクス: 全体 fail-fast → **non-fatal（nil + warn）**
3. name → ID 解決の重複ヒット時挙動: silent take-first → **ambiguity error**
4. Status / Statuses-only クエリの narrowing 必須化
5. MCP `find_estimates/orders/deliveries/receipts.status` schema **削除**（構造的不可、Document Entity に Status なし）
6. `find_invoices.project_name` / `find_purchase_orders.project_name` / `find_payments.purchase_order_id` に `(NOT YET SUPPORTED)` 警告（schema 残置）
7. Document 4 種は disambiguate ではなく **fanout 検索**
8. E2E テストを 193 ケースから 46 ケースへ再構築

詳細決定経緯: `docs/adr/ADR-001-find-layer.md`

## 1. find_groups の削除（Breaking）

旧 v0.6.0:
```sh
board find group --name sales
# MCP: find_groups({"name": "sales"})
```

新 v0.7.0:
```sh
board api groups list --name-cont sales
# users が必要なら: board api users list --group-id <id>
```

理由: Phase H 期から実装が薄く、api 層 Ransack（`name_cont` 等）で完全代替可能。ADR-001 で削除確定。

## 2. enrichment の non-fatal 化（Behavior change）

`board find` 系は主検索 entity を取得した後、`Project` / `Client` / `Vendor` / `Branches` / `Contacts` 等を補助フィールドとして付与（enrichment）します。
v0.7.0 ではこれらの取得失敗を **非致命** に変更しました。

| 項目 | v0.6.0 | v0.7.0 |
|------|--------|--------|
| enrichment 失敗時 | 全体 error | 当該フィールド `nil` / 空配列、`slog.Warn` ログ、主 entity は返る |

**対処**: MCP / CLI 利用側で `Result.Project` / `Result.Client` / `Result.Vendor` 等の nil チェックを追加してください。

```go
// 旧: error がなければ Project は必ず非 nil 前提
res, err := svc.FindInvoice(ctx, q)
fmt.Println(res.Project.Name) // v0.7.0 では panic 可能性

// 新: nil チェック必須
res, err := svc.FindInvoice(ctx, q)
if res.Project != nil {
    fmt.Println(res.Project.Name)
}
```

警告ログは `slog` 経由で `level=WARN msg="enrichment failed"` として出力されます。

## 3. name → ID 解決の重複ヒット仕様（Behavior change）

`--client-name` / `--vendor-name` の部分一致が複数ヒットしたときの挙動が変わりました。

| 項目 | v0.6.0 | v0.7.0 |
|------|--------|--------|
| 重複ヒット | silent take-first（先頭採用） | ambiguity error + 候補上限 5 件列挙 |
| 対処 | （ユーザー認知不能） | `--id` で曖昧性を解消 |

**対処**: 部分一致のままの呼び出しが error 化する可能性があります。エラーメッセージ中の候補一覧から正しい ID を `--id` / `--client-id` / `--vendor-id` で指定してください。

## 4. Status / Statuses narrowing 必須化（Breaking）

full-scan を回避するため、status のみのクエリは reject されます。

| Tool | 旧 | 新 |
|------|----|----|
| `find_projects` | `--status active` 単独 OK | reject。`--id` / `--client-name` / `--name` / `--text` のいずれかと併用必須（`--status` 単独 / `--statuses[]` 単独不可） |
| `find_invoices` | `--statuses[]` 単独 OK | reject。`--status` 単独は API delegation で OK |
| `find_purchase_orders` | 同上 | 同上 |
| `find_payments` | 同上 | 同上 |

判別軸: BOARD API 側で `status_eq` が delegation 可能か（単独 Status は OK）、`statuses[]` のような複数値は API 不在のため narrowing 必須。

**対処**: status-only クエリ箇所を narrowing 付きに修正してください。

```sh
# NG (v0.7.0 reject)
board find project --status active

# OK
board find project --client-name "Acme" --status active
board find project --text "システム" --status active
```

## 5. find2 → find rename（Internal API のみ）

開発期に `internal/service/find2/` で実装していた新 find 層を、N07b で `internal/service/find/` へ rename しました。

**外部利用者への影響なし**: 外部公開 API は `service.FindClient` / `service.FindProject` 等の receiver メソッドのみで、パッケージパスは変わりません（旧 find/ を完全削除して新コードを同名パスで配置）。

仮にこのリポジトリを `replace` で参照していた場合も、import path は同一のまま。

## 6. Document 4 種 fanout 検索（Behavior change）

Estimate / Order / Delivery / Receipt は Document Entity に Status / 主 ClientID を保持しないため、`--client-name` / `--project-name` の対応方針が以下に変わりました。

| 動作 | v0.6.0 | v0.7.0 |
|------|--------|--------|
| `--client-name` で重複ヒット | （未対応 / 一部 take-first） | **fanout**: マッチした全 client / project の document を集約検索 |
| 1 件に絞りたい | （困難） | `--project-id` を使用 |
| delivery / receipt の配列 | `[0]` のみ参照 | **配列全件ループ**で完全網羅 |

disambiguate 系（projects/invoices/purchase_orders/payments）と挙動が異なるため、結果件数が増える可能性があります。

## 7. MCP schema 刷新（Breaking）

LLM が tool シグネチャから機能を誤解しないよう、schema を刷新しました。

### 7-1. 削除（schema レベル）

- `find_estimates.status` / `find_orders.status` / `find_deliveries.status` / `find_receipts.status`
- 理由: Document Entity 4 種には Status フィールドが**構造的に存在しない**（恒久的に追加されない、D1）
- LLM プロンプトで `status` を渡していた場合、handler reject により `status filtering is not supported for documents (no Status field on entity)` を返します（primary defense として handler reject を残置）

### 7-2. 警告（schema 残置 + description で `(NOT YET SUPPORTED)`）

- `find_invoices.project_name`
- `find_purchase_orders.project_name`
- `find_payments.purchase_order_id`
- 理由: 構造的には実装可能だが現時点で未配線（D4: contingently unimplemented）。将来拡張予定として schema は残しつつ、description で警告。

### 7-3. description 全面刷新

- 11 tool 全ての description を統一フォーマット（用途・disambiguate vs fanout・unsupported flag 警告）に書き直し
- `find_projects.status` の narrowing 必須化を description に明記
- helper 4 種（`disambiguateNameDesc` / `fanoutNameDesc` / `notYetSupportedDesc` / `limitDesc`）で生成統一

詳細: `docs/api-reference.md` / `docs/specs/board_cli_mcp_ultra_detailed_design_ja.md §23`

## 8. E2E 構造変更（Internal）

| 項目 | v0.6.0 | v0.7.0 |
|------|--------|--------|
| E2E 関数数 | 47 | Service 41 + MCP handler 5 = **46** |
| ケース数 | 193 | 46（**78% 削減**） |
| 実行 | `go test -tags e2e ./...` 一括 | **per-batch**（Find メソッド単位、rate-limit 配慮）+ CI 非実行（ローカル開発者手動） |
| SKIP ログ | 個別記述 | **統一テンプレ 4 種** `[SKIP:no-creds\|no-data\|cache-warm\|rate-limit] msg`（grep 集計対応） |

**対処**: ローカル E2E 実行時は README "Testing" セクションのコマンド例を参照してください。

## 確認手順

1. `board --version` で 0.7.0 を確認
2. `board mcp serve` 起動後、tools/list で **11 tool**（`find_groups` なし）を確認
3. 既存の MCP / CLI 呼び出しコードで `Result.Project` / `Result.Client` / `Result.Vendor` の nil チェックを追加
4. status-only クエリ箇所を narrowing 付きに修正
5. `find_estimates/orders/deliveries/receipts` の `status` パラメータ参照を全削除
